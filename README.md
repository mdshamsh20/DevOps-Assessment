# Terraform + Database Reliability Assessment

This repo is a small infrastructure and database exercise. The AWS side is Terraform-only; the PostgreSQL steps run locally in Docker, so the examples can be checked without an AWS account.

## Repository layout

```text
infra/
  modules/
    network/
    ecs/
    rds/
  envs/
    dev/
    prod/
db/
  migrations/001_create_tables.sql
  seed.sql
docker-compose.yml
scripts/
  backup.sh
  restore.sh
```

## AWS infrastructure

The Terraform design is `Internet -> public ALB -> private ECS/Fargate tasks -> private RDS PostgreSQL`. The ALB accepts HTTP on port 80. The ECS task uses the public `nginx:1.27-alpine` image as a placeholder and runs in private subnets; its security group accepts port 80 only from the ALB security group. RDS has no public endpoint and accepts PostgreSQL traffic only from the ECS security group. The network module provisions two public and two private subnets, with a NAT gateway for private-subnet egress.

Dev and prod have separate root modules, variables, tfvars and local backend configuration. Dev uses smaller tasks and database sizing, a 7-day backup retention period, and no deletion protection. Prod uses larger sizing, 35-day retention, and deletion protection. Both roots keep state in their own `terraform.tfstate` file; for a team deployment, migrate each local state to a separately provisioned, access-controlled S3 backend with locking before applying.

The dev network uses one NAT gateway to keep the example's running cost down. Prod uses one per availability zone, and enables Multi-AZ for RDS. NAT gateways and Multi-AZ databases add ongoing cost. The example ALB listens on HTTP only; add an ACM certificate and an HTTPS listener before exposing a real production service.

Terraform prerequisites: Terraform 1.5+ and network access to download the AWS provider on first initialization.

```sh
cd infra/envs/dev
terraform fmt -check -recursive ../..
terraform init
terraform validate
AWS_ACCESS_KEY_ID=testing AWS_SECRET_ACCESS_KEY=testing \
  AWS_EC2_METADATA_DISABLED=true \
  terraform plan -refresh=false -var-file=terraform.tfvars
```

Repeat from `infra/envs/prod` for the prod configuration. The plan command supplies dummy environment credentials so Terraform can review the configuration without real AWS credentials; provider settings skip credential/account validation, and `plan` does not create resources. Do not use the dummy values for `apply`: an apply requires real AWS credentials and will create billable resources. Review costs and configure real state storage before applying. The generated RDS password is sensitive but is stored in Terraform state, so protect the state file.

The provider uses `us-east-1` and the example availability zones in the tfvars files. Change both consistently when selecting another region.

## Local PostgreSQL exercise

Requirements: Docker with the Compose plugin. Compose does not include a shared default password. Create a local `.env` file and set a unique password before starting the database:

```sh
cp .env.example .env
```

Edit `.env` and set `POSTGRES_PASSWORD` to a unique passphrase generated by your password manager (five or more random words is a good balance between strength and usability). Keep `.env` private; it is ignored by Git. Do not reuse this local password elsewhere. The database port is bound to `127.0.0.1`, so it is not exposed to other machines on your network.

Start PostgreSQL and apply the schema and seed data:

```sh
docker compose up -d db
until docker compose exec -T db pg_isready -U postgres -d hotel_bookings; do sleep 1; done
docker compose exec -T db psql -U postgres -d hotel_bookings \
  -f /dev/stdin < db/migrations/001_create_tables.sql
docker compose exec -T db psql -U postgres -d hotel_bookings \
  -f /dev/stdin < db/seed.sql
```

The seed inserts 120 bookings across several cities, organizations, and statuses, along with events for a subset of bookings. The SQL files are intended for a fresh database; the seed is not designed to be run repeatedly.

Verify the seeded records and the optimized query:

```sh
docker compose exec -T db psql -U postgres -d hotel_bookings -c \
  "SELECT COUNT(*) AS bookings, COUNT(DISTINCT city) AS cities,
          COUNT(DISTINCT org_id) AS organizations
   FROM hotel_bookings;"
docker compose exec -T db psql -U postgres -d hotel_bookings -c \
  "EXPLAIN (ANALYZE, BUFFERS)
   SELECT org_id, status, COUNT(*), SUM(amount)
   FROM hotel_bookings
   WHERE city = 'delhi'
     AND created_at >= NOW() - INTERVAL '30 days'
   GROUP BY org_id, status;"
```

The bookings index starts with `city` because the query filters on that value, then `created_at` for the date range. It includes the columns needed by the aggregate, so PostgreSQL may be able to answer from the index alone once visibility information permits. With only 120 rows, a sequential scan may still be faster; check the plan rather than expecting the index to win on a tiny sample. The events index helps retrieve a booking's event history in time order.

## Backup and restore

The scripts use the Compose service and read the resolved database user/name from its running container, so Compose environment overrides are honored. Start the service and initialize it before making a backup:

```sh
docker compose up -d db
# Apply the migration and seed steps above first.
./scripts/backup.sh
```

The backup is a timestamped PostgreSQL custom-format dump written under `backups/` (or to the directory supplied as the first argument). To restore it to a fresh database named `hotel_bookings_restore`:

```sh
./scripts/restore.sh
```

To select a dump or target database explicitly:

```sh
./scripts/restore.sh backups/hotel_bookings_YYYYMMDDTHHMMSSZ.dump hotel_bookings_restore
```

Restore drops and recreates only the requested target database; do not point it at a database you need to preserve. It does not modify the source `hotel_bookings` database. Verify the restored copy:

```sh
docker compose exec -T db psql -U postgres -d hotel_bookings_restore -c \
  "SELECT COUNT(*) AS bookings FROM hotel_bookings;
   SELECT COUNT(*) AS events FROM booking_events;"
```

The counts should match the source database. Stop and remove the local database container when finished:

```sh
docker compose down
```
